開新專案 問題迭代

和 AI 迭代問題：怎麼讓開發越改越穩

東西做出來之後怎麼一輪一輪改，還有同樣的錯怎麼不再犯第二次。

先講結論

迭代要穩，重點是每一輪結束時多做一件事：把這一輪被糾正的地方，寫進 AI 下次一定會讀到的檔案。少了這一步，同樣的錯過一陣子就會再出現。

基本迴圈

第一版做出來之後，做的事很單純：自己實際用，看到不對的地方講一句，改完再用。像房子蓋好一間先住進去，哪裡不順再請師傅調。

  1. 1跑起來，自己用AI 說好了不算
  2. 2一句話一句話回報看到什麼講什麼，貼截圖
  3. 3小改直接講，大改先出短計畫新功能照開新專案的最後一步來
  4. 4滿意就定版存檔、推上去、更新說明
  5. ↻回到第 1 步，做下一件
第 1 步

跑起來，自己用

AI 說做好了不算數。要它部署或啟動起來，然後自己實際操作一遍。沒看到實際結果，就沒辦法判斷做得對不對。

要求部署出現 11 次。

講法

部署上去，我要實際用用看。
第 2 步

一句話一句話回報

回報很短。訊息長度的中位數是 31 個字，四分之三在 69 個字以內。

技巧：一次講一件。三個問題分三句講，AI 不容易漏掉。

技巧：講看到的現象。不用猜原因，也不用想怎麼修。

技巧：畫面的問題貼截圖。不用想辦法形容。

技巧：拿原本的設計來對照。有參考圖的時候，講「位置跟圖不一樣」比形容該放哪裡清楚。

技巧：先請它研究，再決定修不修。問題看起來奇怪的時候，講「幫我研究一下」。聽完原因，再回一句「那就修正吧」。

技巧：懷疑不是程式的問題就講出來。例如「是金鑰的問題嗎？我換了一個，再送一次看看」。

回報大概長這樣（改寫過）

  • 手機上排版跑掉了。
  • 好像可以，但顏色還有點刺眼。
  • 按鈕的位置跟圖不一樣。
  • 這個功能有做嗎？
  • 那就都補完吧。

附圖出現 23 次。

第 3 步

小改直接講，大改先出短計畫

調位置、改文字、修一個錯，一句話講完就讓它改。

要加一個新功能，或是會動到資料怎麼存，就先切到計畫模式出一份短計畫，看過再做。做法和〈開新專案〉的第 6 步一樣。

紀錄裡有 10 份計畫，每一份只對一個功能。

第 4 步

滿意就定版

確定這一版可以，才存檔。請 AI 把修改存進版本紀錄再推上去，順便更新說明文件。之後做壞了，可以退回這一版。

要求 commit 或 push 出現 16 次。

講法

這版可以。commit & push，README 更新一下。

同樣的錯一直重複，怎麼辦

常見的狀況是這樣：某個錯已經糾正過，AI 也改對了。過了幾天，同一種錯又出現。再糾正一次，過幾天又來。

AI 不會自己記住

AI 不會從對話裡學到東西。開一個新對話，之前講過的全部歸零。同一個對話拖得太長，前面的內容會被工具自動壓縮，糾正過的細節也會跟著不見。

像工地每天來的都是新師傅。手藝很好，但沒看過昨天的工地，也沒聽過昨天交代的事。

口頭交代的規矩，隔天就沒人知道。規矩要貼在工地門口。

貼在門口的那張紙就是守則檔。Codex 讀的是 AGENTS.md，Claude Code 讀的是 CLAUDE.md。每次開工它都會先讀這個檔。

問題出在流程，不在 AI 懂多少

遇到重複犯錯，很容易解讀成 AI 對這個領域不熟、看過的資料不夠多。這個解讀會讓人覺得只能等更強的模型。

「第一次寫錯」和「糾正過還一直錯」是兩件事。第一次寫錯，可能跟 AI 懂多少有關。糾正過還一直錯，是因為那次糾正沒有被留下來。

換成更強的模型，新對話一樣不知道上次被糾正過什麼。

所以要改的是自己的流程：每次糾正之後，有沒有一個固定的動作把它留下來。

四個做法

  1. 錯第二次就寫進守則檔。寫三樣：錯的寫法、對的寫法、怎麼分辨該用哪一個。可以直接叫 AI 寫：「把剛剛這個錯整理成一條規則，加進守則檔。」
  2. 固定不變的前提寫在守則檔最上面。用什麼工具、第幾版、怎麼啟動、怎麼測試。這些每次都一樣的事，不該每次重講。
  3. 不讓它憑印象寫。把原始碼或官方文件放在哪裡告訴它，規定用到不確定的名稱之前要先去查。
  4. 改完當場跑一次。每次改完都實際啟動或安裝一遍，把完整的錯誤訊息原封不動貼回去。能自動檢查的規則交給工具來擋，不靠 AI 自己記得。

守則檔大概長這樣

# 專案守則
- 這個專案用〈工具名稱〉第〈幾〉版。
- 啟動方式：〈指令〉。測試方式：〈指令〉。
- 用到不確定的名稱之前，先去〈原始碼或文件的位置〉確認它存在。
- 改完一定要實際跑一次，並貼出完整的錯誤訊息。

## 被糾正過的事
- 不要〈錯的做法〉，改用〈對的做法〉。原因：〈一句話〉。
- 不要〈錯的做法〉，改用〈對的做法〉。原因：〈一句話〉。
（每被糾正一次就加一條）

守則檔不用一開始就寫得很完整。重點是每次被同一個錯絆到第二次，就多一條。幾個禮拜之後，這份檔案會變成這個專案專屬的注意事項。

這個迴圈裡沒有的東西

  • 驗收不靠自動測試。靠的是部署之後自己實際用。
  • 沒有常換對話。最長的一條對話用了 184 個回合，中間被工具自動壓縮 38 次。
  • 沒有另外找一個 AI 來審查。

完整版：大型專案上的九個做法

上面四個做法是最小的版本。下面是同一個人在多人維護的大型專案上實際在用的完整版。思路一樣：把被糾正過的事寫成檔案和機制，讓下一次對話自動帶著。

九個做法

  1. 規則寫成指示檔：全域一份（shell 環境的坑、註解和語言規則、驗證要求），專案一份（命名約定、架構模式、文件入口）。
  2. 糾正一次就存成記憶：每條一個檔，寫規則、為什麼、什麼時候套用，另有一份一行一條的索引。
  3. 重複流程做成 skill：開卡、寫 MR 描述、自審、日報、口吻潤飾各一個，不用每次重講格式。
  4. 硬規則用 hook 擋：沒自審過的 git commit 會被攔下來。唯讀探索累積太多會跳提醒。
  5. 找問題和驗問題分開：review 找到的每條重要 finding，另開一個乾淨 context 的代理專門反駁，駁不倒才算數。
  6. 狀態寫檔：finding、修正的 commit、每輪結論都進狀態檔，下一輪先核對上一輪修好沒。
  7. 證據紀律：對 runtime 行為下結論要附檔案和行號。沒跑過的驗證不寫成通過。subagent 回報的 API 形狀要自己再確認。
  8. 保護主線 context：大量搜尋和長 log 丟給 subagent 只收摘要。告一段落先把結論寫進筆記再清對話。走錯路用回溯，不用摘要壓縮。
  9. 對外動作留給人：留言、resolve、@人只準備草稿。多項決策逐項核可，沒點名的不動。

一張卡從頭到尾的流程

  1. 從卡片開始：先覆述理解、確認規格，有歧義先問。
  2. 寫實作計畫，開獨立分支或 worktree。
  3. 方案定案後降階模型做實作。
  4. 每次 commit 前自審：審 diff、寫狀態檔、修、登記、再 commit。
  5. 用 skill 產 MR 描述，再跑一次 MR 層級的自審。
  6. 要給別人看的文字先過口吻潤飾，由本人貼出去。
  7. 收尾把結論寫進記憶或筆記，再清對話。

三個片段

指示檔裡的一條規則

## Answering & Verification
- 對 runtime 行為、設定預設值下結論之前，先附上驗證過的檔案與行號。
  沒讀過原始碼就明講「未經驗證的假設」。

一條記憶

---
name: verify-subagent-api-claims
description: subagent 回報的 API 形狀寫進程式碼前要自己確認
---
巢狀、命名空間、簽章先 grep 既有呼叫端或讀定義。
**Why:** 曾照摘要寫，編譯才發現簽章不對。
**How to apply:** 寫進程式碼前；push 前先本機 build。

驗證代理的開場

You are verifying ONE code-review finding adversarially.
Your job is to try to prove it WRONG. Only if you cannot, confirm it.
Check in order: contract, upstream guard, reachability, pre-existing, severity.

一個實際例子：請第二個 AI 來查證

AI 檢查自己做的東西，有時候會報出其實不存在的問題。照著去修，反而把好的地方改壞。

做法是另外開一個新的對話，請第二個 AI 來查證。它沒看過前面的討論，只拿到那一條疑慮，任務是想辦法證明這條疑慮是錯的。

實際發生過的一次：

  1. 要做的事是把專案裡用到的一個工具換成新版。
  2. AI 改完之後自己檢查，回報了兩個問題。嚴重的那個是「新版少了一個功能，專案會跑不起來」。輕微的那個是「有個設定之後可能會被自動改掉」。
  3. 沒有馬上去修。另外開了第二個 AI，只問它一件事：新版真的少了那個功能嗎？
  4. 第二個 AI 去讀了新版的更新說明，上面沒有寫拿掉那個功能。它也查到專案在新版上實際跑成功過。
  5. 結論是嚴重的那個問題不存在。只把「查過了、為什麼不成立」記下來，免得下次又被提一次。輕微的那個記下處理方式，之後再處理。

如果當時直接照第一個 AI 說的去修，會白花一輪，還可能把原本好的東西改壞。

模型挑選

兩個工具上的做法不一樣。Claude Code 上有一套按工作分級的守則。Codex 上的紀錄是一律用當下最新的模型，思考程度開到 high 以上。

Claude Code：按工作分級

原則是先分「答案用查的」還是「答案用推的」。方案定案後就降階做實作，高階額度留給 review 和決策。

工作類型模型思考程度

中途降階的時機是「開始寫 code、跑驗證、等 CI」那一刻。

思考程度怎麼挑

  • low：答案是查出來的。搜尋、列舉、格式轉換。
  • medium：預設。有明確做法、照著做就對的實作。
  • high：需要交叉驗證或分支推理，錯了難發現。
  • 更高：只用在想錯會浪費半天以上的場合。

這份整理的限制

  • Codex 的紀錄只涵蓋本機還留著的近一個月對話，三個專案、584 則訊息。更早的不在統計裡。
  • 出現次數是用關鍵字數的。意思一樣但講法不同的不會算到，所以數字偏低。
  • 「套同一套分級」那張表是照官方模型頁的定位推出來的，不是官方對照表，也沒有實際使用紀錄。
  • Codex 的額度是否依模型分開計算沒有查到。官方頁只說 Sol 每 token 花的 credit 比 Astra 少。

給新手的建議

下面是假設完全沒有經驗的人要開始，從上面的做法裡挑出來的最小版本。這一段是建議，不是紀錄。

  1. 一次只講一件事。看到三個問題就分三句講。
  2. 講看到的就好。「按了沒反應」「字疊在一起」就夠了。不用猜原因，那是 AI 的工作。
  3. 畫面的問題貼截圖。
  4. AI 說改好了，自己操作一次再說好。
  5. 滿意一版就請它存檔。講「這版可以，幫我 commit」。之後改壞了，可以請它退回這一版。
  6. 同一個問題改了三次還沒好，先停下來。改成請它研究原因、說明給人聽，聽懂了再決定要不要修。
  7. 看不懂就問「這是什麼意思」。會花錢、會刪資料的動作，問清楚再答應。
  8. 平常用工具預設的模型就好。高階模型額度用得比較快。同一個問題改了幾次還沒好的時候，再換成高一級的模型試一次，解決了就換回來。
  9. 同一個錯出現第二次，就寫進守則檔。講一句「把剛剛這個錯整理成一條規則，加進守則檔」就可以。重複犯錯要靠這一條來擋。
  10. 「完整版」那一大段先不用看。四個做法做順了，覺得還不夠再回來看。
